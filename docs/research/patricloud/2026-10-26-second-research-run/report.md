# Front Clutter with a stable contract

Patrii Cloud at [patrii.cloud](https://patrii.cloud/) is the product behind the spellings PatriCloud, patriicloud, and “patrri cloud”: a Montreal OpenStack public cloud, sold by Patrii Québec inc. on technology owned by Patrii Cloud inc., in public beta since **18 June 2026**. It has a live JSON API at `https://api.patrii.cloud` and no published diagram, plan, or apply model, so it cannot be the standard other products call. Clutter, built for Alberta 2514640 Inc., already has the intent model those products need — organization, project, diagram, cloud account, and a run — and that model should become the versioned contract, with an adapter process placed **in front of Clutter’s API Gateway**. Who hosts that process can stay open. Clutter-hosted and caller-hosted are the same contract with different custody of credentials and state. Patrii-hosted is unavailable: Patrii is vendor SaaS, and it publishes no inbound plugin. Clutter’s organization, project, and diagram path, plus the single membership check behind them, are sound enough to wrap. The codebase is an internal product API with a working cross-account AWS run path, and it is not ready to be the standard until machine identity, the unauthenticated compiler, and the customer IAM role are fixed. Current Clutter behavior translates onto that standard as desired state and runs. It does not translate onto Patrii’s resource API, because the compiler only knows five AWS types and Patrii has nothing that receives a diagram.

## Patrii Cloud is a Montreal target with a console for a contract

The name that resolves in public sources is **Patrii Cloud**, domain `patrii.cloud`, GitHub login `PatriiCloud`. Terms updated **7 September 2026** say the service is sold in Quebec and elsewhere in Canada by Patrii Québec inc., on technology owned and operated by Patrii Cloud inc., on servers in Montreal ([Terms](https://patrii.cloud/legal/terms)). The about page dates the founding to **11 July 2025** in Greater Montreal and names Guillaume Harvey as co-founder, CEO, and CTO ([About](https://patrii.cloud/about)). Exact strings PatriCloud, Patricloud, and patriicloud do not identify a second product. Three near misses must stay out of the adapter: **Partiri** (`partiri.cloud`) is a different PaaS with its own CLI, API key file, and an MCP server at `https://mcp.partiri.cloud/mcp` ([Partiri MCP](https://partiri.cloud/documentation/mcp)); **Patr** (`patr.cloud`) is a self-hosted app platform ([patr.cloud](https://patr.cloud/)); Particle, The Patriot Cloud, and Patrimóvel Cloud are unrelated. Nothing in Clutter’s README or a text search of the final-report PDF names Patrii. The sponsor on the README is Alberta 2514640 Inc., and the product described there is a drag-and-drop GUI that generates Terraform and Ansible for AWS ([README](file:///Users/muneebali02/Desktop/re-clutter/README.md)).

Patrii’s own pages describe a Canadian public-cloud beta for startups, agencies, and enterprises: shared VPS, block and S3-compatible object storage, networking, floating IPs, snapshots, custom images, managed PostgreSQL, MySQL, Valkey, and FerretDB, load balancers, DNS, domain registration, TLS certificates, managed Coolify, NFS, and Kubernetes ([Services](https://patrii.cloud/services)). The named stack is **OpenStack Epoxy, Ceph, Open vSwitch with VXLAN, KVM**, with FreeIPA on the homepage ([Homepage](https://patrii.cloud/)). Billing in the terms is quota allocated to the account, in CAD, not hour-metered, and deletion mid-term does not prorate ([Terms](https://patrii.cloud/legal/terms)). The lowest cited instance price is **$5.25 CAD per month** before tax ([Pricing](https://patrii.cloud/pricing)). Hosting is vendor SaaS. Terms place the servers in Montreal. No install, Helm chart, or customer-run control plane appears on the home, services, docs, or API pages. “Managed Coolify on your own instance” is a PaaS Patrii operates. “Private cloud options” sit next to dedicated account management and are still Patrii-operated. Privacy text says data stays in Canadian data centers and that PIPEDA certification is being worked toward ([Privacy](https://patrii.cloud/legal/privacy)). ISO 27001 and SOC 2 Type II are roadmap items, not current certifications ([Services](https://patrii.cloud/services)).

Two surfaces disagree, and the adapter has to follow the one that is actually running. Marketing pages say the REST API, an OpenAPI 3.0 file, six language SDKs, webhooks, rate limits, and a Terraform provider are not yet available, then show sample curls against `https://api.patrii.cloud/v1/instances` with bodies that contradict each other (`type` versus `flavor`, `montreal-1`, ids `inst_1234567890` versus `i-1234567890`) ([API page](https://patrii.cloud/api), [Services](https://patrii.cloud/services), [Documentation](https://patrii.cloud/documentation)). The live host, probed on **26 October 2026**, returned `{"message":"Patrii Cloud API is running","version":"1.0.0"}` from `GET /`, and `GET /docs`, `GET /redoc`, and `GET /openapi.json` returned 404 ([api.patrii.cloud](https://api.patrii.cloud/)). The production console hard-codes `baseURL` `https://api.patrii.cloud` and contains **no `/v1/` string**. Its region string is `COLOGIX-MTL-2`. A private Keystone URL, `http://10.0.0.10:5000/v3`, is baked into the bundle and is not a public endpoint ([console bundle](https://console.patrii.cloud/assets/index-Duo5u5i-.js)). `GET https://registry.terraform.io/v1/providers/patrii/patrii` returned provider-not-found, and `PatriiCloud/terraform` is an empty repository created **14 December 2025** ([Terraform Registry](https://registry.terraform.io/v1/providers/patrii/patrii), [terraform repo](https://github.com/PatriiCloud/terraform)). The root version string `1.0.0` does not mean the marketing `/v1` resources exist.

The console’s de facto contract is what a target adapter can code against today, with the caveat that it will break when the console changes, because there is no spec version to pin. Authentication is a bearer session token. A bad bearer on `GET /v1/instances` produced `{"detail":"Token has expired. Please login again."}`, and a bad `X-API-Key` produced `{"detail":"Invalid API key"}` ([api.patrii.cloud](https://api.patrii.cloud/v1/instances)). The console logs in with `POST /auth/login`, stores `token` and `session_id`, refreshes with `POST /auth/refresh-token` plus `X-Session-Id`, and can redirect to an OIDC `authorize_url` from `GET /auth/oidc/login`. Mutating calls also send `X-CSRF-Token`. The API-key screen tells the user to send the secret as `Authorization: Bearer`, shown once, scoped to a project. The HTTP paths that create and revoke those keys are not string literals in the bundle. `X-API-Key` is attached by the console only on announcement admin calls. The tenant boundary in the client is a **project**: `POST /auth/switch-project` with `{project_id, session_id}`, plus `/projects` CRUD, members, and quotas. No organization resource and no scope string such as `compute:write` appear ([console bundle](https://console.patrii.cloud/assets/index-Duo5u5i-.js)).

Resource families the console actually calls, all unversioned, are compute servers under `/compute/servers` (start, stop, reboot, pause, suspend, rescue, rebuild, resize, snapshots, backups, keypairs, flavors, images, networks, security groups), PaaS Coolify under `/paas/instances`, databases under `/databases`, load balancers under `/loadbalancers`, Kubernetes under `/k8s/clusters`, support, and billing. An audit-route map in the same bundle also names `/networks`, `/storage/volumes`, `/storage/s3`, `/dns/zones`, `/secrets`, and `/certificates` as write patterns. Several of those did not also appear as literal client calls, so they are evidence of intended routes, not proof they respond. The load-balancer client prefix `/loadbalancers` and the audit prefix `/networks/load-balancers` are not safe to treat as aliases. Server actions are asynchronous: the console opens `wss://api.patrii.cloud/ws?token=…` and branches on `server_update`, `lb_update`, `cluster_update`, and announcement types. The word `webhook` does not appear in the bundle. The API page lists webhooks as future work and gives no signature header ([API page](https://patrii.cloud/api)). Errors observed are HTTP status plus a JSON `detail` string. No idempotency key is sent. A French changelog string in the bundle says a retried create once started several identical billable servers. List calls use `force_refresh` and `detailed`, not `page` or `cursor`. Rate-limit headers were present on public GETs (`x-ratelimit-limit: 1000` on `GET /`, `10000` on `GET /health`) even though the docs still call rate limiting future work. The SLA names a 99.9 percent target for API endpoints and excludes features labeled alpha, beta, or preview, while the site banner says the platform has been in beta since 18 June 2026; the SLA document itself is dated **24 July 2025** ([SLA](https://patrii.cloud/legal/sla), [Homepage](https://patrii.cloud/)).

The only connector Patrii describes is its own Lynx DCIM module, which claims to pull inventory from `https://api.patrii.cloud` through a generic cloud-connector framework (servers, networks, volumes, keypairs, images), read-only in v1, default sync **30 minutes**, with write-through left as a future action queue. The module pages required sign-in when fetched, so the paths were not re-read from the origin ([Lynx module index](https://dev.lynx.patrii.ca/modules/lynx_dcim_ipam_cloud)). That is a pull of cloud inventory into DCIM. It is not a hook Patrii uses to invoke an external diagram or Terraform service, and it is not the interface Clutter should implement. No console route contains `diagram`, `terraform`, `plan`, or `apply`. Patrii, in the adapter, has the same role as an AWS account: a project id, a bearer credential, and a resource API the target adapter calls.

## Clutter’s CRUD is wrap-ready and its run path is not a platform

Clutter’s durable model, in the SQL shipped with this tree, is users, organizations, a membership table of `(organization_id, member_id)` with no role column, AWS account-role rows, projects, React Flow diagrams plus history, deployment-log rows, Ansible jobs, and playbooks ([application-tables.sql](file:///Users/muneebali02/Desktop/re-clutter/backend/storage-sql/application-tables.sql)). API Gateway exposes about **31 methods**, one Lambda each, no `/v1` prefix, and no `aws_api_gateway_deployment` or `aws_api_gateway_stage` in this Terraform, so the repo does not by itself publish the API ([api-gateway module](file:///Users/muneebali02/Desktop/re-clutter/backend/infra/modules/api-gateway/main.tf), [infra main](file:///Users/muneebali02/Desktop/re-clutter/backend/infra/main.tf)). Almost every method uses a custom JWT authorizer on the `Authorization` header, result TTL **0**. Three do not: `POST /log-in`, `GET /resources`, and `POST /terraform-engine`. The frontend sends the raw JWT with no `Bearer` prefix. Login accepts a Google ID token, upserts the user by email, and signs an HS256 JWT whose claims are `sub`, `email`, `full_name`, `picture_url`, `created_at`, and `exp` **24 hours** out ([log-in handler](file:///Users/muneebali02/Desktop/re-clutter/backend/api/log-in/main.go), [jwtGeneration.go](file:///Users/muneebali02/Desktop/re-clutter/backend/api/log-in/internal/jwtGeneration.go)). The browser cookie `clutter_token` is set for **7 days**. A search of Go, TypeScript, Terraform, and SQL found no API key, service account, refresh route, or idempotency key. The authorizer parses with library validation turned off and then checks claims itself; its comment says “Google ID Token” while the code verifies the Clutter JWT ([authorizer](file:///Users/muneebali02/Desktop/re-clutter/backend/api/authorizer/main.go)).

Tenancy for the real handlers is one function, `CheckOrganizationMembershipPSQL`: the organization must exist (404) and the caller must be in `organization_members` (403) ([membership.go](file:///Users/muneebali02/Desktop/re-clutter/backend/api/generic/membership.go)). Tests sit beside that function. Diagram update checks node and edge identity, then inserts the previous row into `diagram_history` in the same transaction. Account linking is a deliberate two-phase row. `GET /cloudformation-stack-url/{organizationId}` inserts an `incomplete` role row with a UUID external id and returns a CloudFormation console URL. `POST /organization/{organizationId}/accounts/{accountId}` stores the role ARN only when the row is still incomplete and the ARN suffix matches the server-generated 8-character id ([stack-url generator](file:///Users/muneebali02/Desktop/re-clutter/backend/api/cloudformation/stack-url-generator/main.go), [submit-role-arn](file:///Users/muneebali02/Desktop/re-clutter/backend/api/organization/accounts/submit-role-arn/main.go)). Apply and destroy run as Fargate tasks in Clutter’s account. The task role may assume only `AllowClutterToDeployTerraformRole-*`. The customer template that product asks the customer to click grants `ec2:*`, `lambda:*`, `apigateway:*`, `dynamodb:*`, `s3:*`, `iam:*`, `ssm:*`, and `logs:*` ([client role template](file:///Users/muneebali02/Desktop/re-clutter/backend/infra/modules/s3/uploads/client_side_terraform_deployer_role.yaml)). Ansible validates instance ids against `^i-[0-9a-f]{8,17}$`, rejects a request that sends both a playbook id and an S3 key, and marks the job `FAILED` if the queue send fails. That is a real AWS integration with a visible trust boundary, not a sketch.

The judgment of the tree as it sits is specific. The organization, project, and diagram CRUD path, the membership function, diagram history, and the two-phase account link are the part worth wrapping. They are local, they are enforced in Go and SQL, and an HTTP client that already holds a user JWT can create orgs, projects, and diagrams, submit a role ARN, start apply or destroy, presign a playbook or Lambda zip, and poll logs. The execution path is the part that must not be frozen into a public contract yet. `POST /terraform-engine` is unauthenticated, accepts a Supabase-shaped webhook body, does not verify `type` or `table`, and writes Terraform into `s3://{bucket}/{org}/{project}/{diagram}/`. Diagram update does not call it. The feature the product is named for is off the authenticated write path ([terraform-engine create](file:///Users/muneebali02/Desktop/re-clutter/backend/api/terraform-engine/create/main.go)). Terraform runs write `diagram_deployment_logs` (`apply` or `destroy`, status `RUNNING`, `SUCCESS`, or `FAILED`). Ansible runs write `jobs`, which have no `organization_id` and are listed with `WHERE created_by = $1 LIMIT 50`, and the JSON response includes `role_arn`. The external id travels in the SQS body. There is no single run resource to poll. The compiler’s `ParseResourceType` accepts `lambda`, `dynamodb`, `s3`, `api gateway`, and `ec2` ([mapper.go](file:///Users/muneebali02/Desktop/re-clutter/backend/api/terraform-engine/create/internal/generator/resources/mapper.go)). A seed table and the editor’s config panel are a second and third list of the same labels, and they already drift. The gateway schema allows project names of length 100 and the column is `VARCHAR(32)`. The TypeScript client and the README allow `plan`; the gateway enum is `apply` and `destroy` only. The model description defaults region to `us-east-1`; Go defaults to `us-west-2`. Member administration mutates an in-memory `MOCK_MEMBERS` list and never touches `organization_members` ([members api](file:///Users/muneebali02/Desktop/re-clutter/frontend/clutter/src/lib/features/members/api.ts)). Error bodies are not one schema, and several handlers return raw `err.Error()`. CORS on the shared response helper is `*`. `GET` that creates an account-link row is unsafe to retry.

Readiness is “internal product API with a browser login,” not “platform API.” The seams are visible and local. The blockers are a handful of trust and contract bugs, not the absence of a framework. Wrapping the Next.js app would wrap mocks and a canvas. Wrapping API Gateway wraps the real model, plus the public compiler and the admin-sized role, which have to be fixed in Clutter before the wrapper is safe to hand to another product. The smallest changes that make the wrap honest, short of a rewrite: a non-human mint path beside the Google exchange that still ends in `CheckOrganizationMembershipPSQL`; close `POST /terraform-engine` with the authorizer or a shared secret and make diagram save and compile one authenticated sequence; narrow `iam:*` and `s3:*` on the customer template before any other account is asked to deploy it; stop returning `role_arn` on job JSON and stop using `jobs.created_by` as the tenant key; idempotency on account-link creation and job submit; one error envelope at the boundary; align the project-name length; and drop `plan` from any published type until a handler exists.

## The adapter sits in front of the gateway, and hosting only moves custody

The adapter is a new process that other products call. It is not a plugin inside Next.js, not a Patrii inbound interface (none exists), and not the Lynx DCIM connector. It speaks a versioned resource API and translates that API into the handlers that already exist. Internal Clutter paths stay the dialect. Callers never learn that projects are query parameters, organizations are path parameters, and logs use `orgId` while the rest of the API uses `organizationId`.

Six principles fix the boundary before anyone picks a host. Clutter owns intent and clouds own resources: callers submit organizations, projects, a desired-state document, a cloud account, and a run; a target adapter turns a run into AWS Terraform or Patrii REST, and callers do not send ARNs or Patrii paths as the standard’s vocabulary. Every caller, human or service, resolves to a user id that `CheckOrganizationMembershipPSQL` accepts, so machine auth is a new mint beside Google, not a bypass of membership. Compile and apply are one authenticated sequence: a diagram save that does not compile, and a public webhook that does, cannot be the contract. The adapter is the only versioned surface (`/v1`, one error envelope, one id style, an idempotency key on creates), because neither Clutter nor Patrii documents idempotency and Patrii’s own UI copy records duplicate billable creates. Hosting moves the process and not the custody rules: whoever runs the adapter holds target credentials and state, and those credentials stay server-side. The current trust boundary is not part of the standard: publishing today’s customer role template, or today’s open compiler, would standardize a full-admin cross-account role and an unauthenticated write into Clutter’s bucket.

The same placement holds under all three hosting choices. The standard HTTP process, the identity broker, the Postgres model, and the compiler are one deployable. The runner is a second deployable that has to sit where it can assume the target role or call the target API, and where the state files live.

| Piece | Clutter-hosted | Caller-hosted | Vendor-hosted |
|---|---|---|---|
| Versioned API other products call | Runs next to API Gateway in Clutter’s account | The caller runs the same process, or calls a remote Clutter deployment | Patrii does not offer this. A Clutter SaaS run by Alberta 2514640 Inc. is the Clutter-hosted column |
| Identity | Clutter mints a service credential that still maps to a member row; Google login remains a client of the same rule | The caller presents that credential to remote Clutter, or runs the mint if they self-host the whole stack | A Patrii bearer is a cloud credential on a cloud-account object. It is never the Clutter identity |
| Diagram store | Clutter Postgres, `diagrams.data` JSONB | Same schema wherever Postgres runs | Patrii has no diagram resource |
| Compiler | Authenticated compile in the existing Lambda, writing the existing S3 layout | Same binary | No Patrii compile step |
| AWS apply / destroy | Clutter Fargate assumes `AllowClutterToDeployTerraformRole-<id>` | The caller runs the runner only if they hold that principal; the customer role still has to exist in the target account | Unchanged. Patrii does not participate in the AWS handshake |
| Patrii apply | The target adapter calls `https://api.patrii.cloud` with the project bearer | Same calls, from whoever holds the token | Patrii is the target, not the host of the adapter |
| State files | Clutter S3 at `{org}/{project}/{diagram}/` | The caller’s bucket if they self-host execution | Patrii has no Terraform state API. State remains Clutter data |
| Events back to callers | The adapter emits them. Clutter today only offers polled log GETs with `nextToken` | Same | Patrii’s `/ws` socket is a console session channel, not a callback Patrii will send to Clutter |

Caller-hosted does not mean the caller reimplements Terraform. It means the caller runs the adapter process and therefore holds cloud credentials. Clutter-hosted means Clutter stores those credentials the way it already stores a role ARN and external id, and the Fargate task keeps assuming into the customer account. The human CloudFormation click remains in the customer account either way; nothing in this API creates that stack. Vendor-hosted splits in two, and only one of the two exists. If the vendor is Clutter’s sponsor, the deployment is the first column offered as SaaS. If the vendor is Patrii, there is no place to install the control plane: terms put the servers in Montreal under Patrii Cloud inc., and no page offers a customer-installed Patrii. Pointing a Clutter-hosted adapter at Patrii also chooses data residency. Diagram JSON, generated Terraform, and state would sit wherever Clutter is hosted, while the resources those files describe would sit in Montreal. Patrii’s privacy text says Patrii stores customer data in Canada. An adapter outside Canada that uses the customer’s own Patrii token is the customer’s call, and it should be an explicit deployment choice before the first Patrii cloud account is saved.

What an external caller can already do, once it holds a Clutter JWT, is the internal dialect the adapter hides. Organization CRUD, project CRUD, diagram CRUD, account list and delete, role-ARN submit, the CloudFormation URL, terraform apply and destroy, log reads, code-upload and playbook presigns, and Ansible submit and get are real routes ([infra main](file:///Users/muneebali02/Desktop/re-clutter/backend/infra/main.tf)). `GET /resources` and `POST /terraform-engine` are callable with no JWT. What no route provides, and what the standard must not pretend exists, is inviting a member, setting a role, refreshing or revoking a token, registering a service account, running `plan`, and reading diagram history. History is written and never exposed. S3 upload is a second hop the caller can perform after the presign, without Next.js. Canvas editing has no API of its own. The API is “replace `data`,” and `data` is a React Flow document: nodes with `id`, `type`, `position`, and `data`, edges with `id`, `source`, and `target` ([models_diagram.go](file:///Users/muneebali02/Desktop/re-clutter/backend/api/generic/models_diagram.go)). The adapter should accept a neutral desired-state document and emit that struct, so callers do not learn `@xyflow/react`. Until that translation exists, the only document both the editor and the compiler read is the canvas file.

## Clutter’s behavior becomes five standard objects, and Patrii receives only the cloud account

The standard other products call has five objects, mapped from behavior that already exists, with names chosen so Patrii’s “project” and Clutter’s “project” do not collide. A **workspace** is Clutter’s project: a named container under an organization. A **cloud account** is a credentialed target. Today that row is `aws_account_access_roles`. Under the standard it is the same idea with a provider field, so a Patrii project id plus a bearer token is a second provider on the same object, not a second tenancy model. A **desired state** is the diagram. A **run** is the thing callers poll. Today they would have to poll two tables. A **catalog** is the resource types the compiler will accept. Membership stays boolean until a role column exists; the UI’s “Project Admin” string is not data and must not appear in the contract.

| Standard object | What the caller sends | Clutter behavior today | Patrii side |
|---|---|---|---|
| Organization | Name, then member operations once a real member API exists | `POST/GET/PUT/DELETE /organization`. Creator becomes the only member. No invite route | No organization resource. Do not invent one |
| Workspace | Name under an organization | `POST/GET/PUT/DELETE /project`, query-param ids, name column 32 characters | Patrii’s project is not this. It is the cloud tenant |
| Cloud account | Provider, display name, then a link ceremony | AWS: a GET that inserts an incomplete row and returns a console URL, then a POST of the role ARN. Each GET inserts another row | Store a project id and a bearer created in the Patrii console at `/app/api-keys`. Call `POST /auth/switch-project` if the token is not already scoped. Key-management paths are not in the bundle, so minting stays a human step in Patrii’s UI, analogous to the CloudFormation click |
| Desired state | A neutral graph the adapter writes as React Flow JSON | `PUT /diagram` replaces `data`. Structural checks only. Save does not compile. A canvas that cannot compile still saves | No diagram, plan, or apply resource. Nothing on Patrii receives this document |
| Catalog entry | Type and variables | Seed labels Lambda, S3, DynamoDB, API Gateway, EC2 Container. Compiler switch: `lambda`, `dynamodb`, `s3`, `api gateway`, `ec2`. Adding a sixth type means a seed row, a Go switch, a generator, S3 templates, and a UI branch | Servers, volumes, networks, load balancers, databases, Kubernetes, DNS, S3-compatible objects, Coolify. None of the five Clutter types is a Patrii type. EC2 is the nearest neighbor of `/compute/servers` and still compiles to AWS Terraform |
| Compile | Workspace id and desired-state id, authenticated | `POST /terraform-engine` with a Supabase webhook body, no JWT, writes S3. Not called by the frontend client | No compile step |
| Run | `apply` or `destroy`, cloud account, region | `POST /terraform-command-runner` returns `commandId` and `taskArn`. Schema does not require the account id; a missing id becomes a 500 from the database lookup. Fargate env is `CLIENT_ROLE_ARN`, `ASSUME_ROLE_EXTERNAL_ID`, `TERRAFORM_DIRECTORY`, `COMMAND`. Logs are four GETs under `/terraform-engine/logs` | A Patrii run is the target adapter calling `/compute/servers` and the related families, then polling the resource or, if a session token is all that exists, listening on `/ws`. There is no jobs resource and no documented webhook for Patrii to call back |
| Config job | Playbook and target ids | `POST /ansible/jobs` returns 202 `QUEUED`. Targets must match AWS instance ids. Listed by creating user, cap 50 | The instance-id pattern rejects Patrii server ids. Ansible does not translate |
| Events | Subscription on the adapter | Poll `nextToken` until the UI’s notion of `STOPPED`. No websocket on Clutter | Console socket types `server_update`, `lb_update`, `cluster_*`. Not a published third-party stream. `status.patrii.ca`, named in the SLA, did not resolve; the public status page is [patrii.cloud/status](https://patrii.cloud/status) |

That table is the full translation. Control-plane objects move onto the standard by renaming and tightening what the Lambdas already do. Resource instances do not move onto Patrii at all until a new generator family exists. Shipping the five AWS types through a Patrii bearer would create AWS resources in whatever account the role ARN points at, and would leave the Patrii project empty. The Patrii target adapter is new code beside `ParseResourceType`, not a mapping table of Lambda onto a VPS. Its first honest operations are the ones the console already performs and a read-only inventory would need anyway: list and get servers, flavors, images, keypairs, networks, volumes, and DNS zones; create and delete a server; poll `task_state` or provisioning status. Write schemas for create-server are not in the bundle. The console passes through UI objects that were not inlined, so the first Patrii writes have to be captured from a real console session or delayed until Patrii ships the OpenAPI file it already promises. OpenStack service endpoints are not the supported surface. The homepage says “full API compatibility” and names Terraform, Ansible, and Kubernetes, and it never names Nova, Neutron, or Keystone ([Homepage](https://patrii.cloud/)).

Other products, Patrii included, call the five standard objects and nothing else. A caller creates an organization, a workspace, and a desired state, attaches a cloud account by completing that provider’s link ceremony, and starts a run. Clutter calls Patrii. Patrii does not call Clutter. A Patrii-side integration that only wants inventory, which is what Lynx already sketched, is a read of the cloud-account’s resources through the same target adapter, on a poll interval, and it still does not push a diagram back into Patrii. Service accounts are how those products authenticate, after the mint path exists. Until then, the only way in is a Google ID token for a human who is already a member, reused as a 24-hour JWT, and that is impersonation rather than an integration.

## Conclusion

The adapter is worth building as a thin, versioned front on the handlers that already match the product’s real model, and it is not worth building as a client of Patrii’s marketing samples or as a plugin Patrii will call. Patrii is a young sovereign-cloud beta with a working console API and an explicit gap where the developer contract should be. Clutter is a credible AWS diagram runner with tested membership and a dangerous, unfinished edge. Treating the console paths as a stable SDK, or treating Clutter’s current routes as a platform, would lock both gaps in place.

The decision that stays open is only where the adapter process runs. The decision that should not stay open is the shape of the contract: Clutter-owned intent, a cloud account per target, authenticated compile-then-run, and a Patrii client written against `/compute/servers` and its sibling families when, and only when, a desired state is actually aimed at a Montreal project. Narrow the customer role and close the public compiler first. After that, another product can connect without learning React Flow, Supabase webhooks, or which of Patrii’s two documented APIs is fiction.
