# backend/infra

Platform Terraform: deploys Clutter itself into Clutter's AWS account. Rules for Terraform here and for the customer templates under `modules/s3/uploads/` are in `.claude/rules/terraform.md`.

Traps:

- **Applied by a person, never from a session.** The `guard-cloud-writes` hook asks before any apply, destroy or state edit. Never run `plan` against the real backend from a session: it reads state that holds secrets.
- **A Lambda route is public unless its integration module gets `jwt_authorizer_id`.** The integration template sets `authorization = "NONE"` when it is missing.
- **Each customer template is uploaded by its own `aws_s3_object` in `modules/s3/main.tf`.** A new template file needs a new object block.
- **The customer role (`modules/s3/uploads/client_side_terraform_deployer_role.yaml`) lists named actions only**, for exactly what the templates render (A's five, B's three, B's IAM and override files, A's IAM step and Ansible over SSM). A template that renders a new resource type needs its actions added here, or the first deploy fails; widening it needs a reason in the PR, and `RoleTemplateVersion` moves with every change, in the same change as `RoleTemplateVersion` in `backend/adapter/connectors/aws/aws.go`.
- **The customer role changes or deletes only resources tagged `ManagedBy` (`Clutter`, or `Ansible` on instances), and creates one only with that tag in the create request.** The provider's `default_tags` put `ManagedBy = Clutter` on everything (A's `writer.GenerateMainTF`, B's `tmpl/provider.tf.tmpl`); keep it there. A new resource type needs its create, change and delete actions under the matching tag statements, and a create that cannot carry the tag fails with access denied. No statement may let the role add `ManagedBy` to a resource that lacks it: that tag is what keeps the account owner's own resources, and SSM on their instances, out of reach. S3 bucket actions carry no tag condition (S3 checks bucket tags only with per-bucket ABAC, which the AWS provider 5.x cannot switch on).
- **The customer role may create, change or pass only roles, instance profiles and users under the path `/clutter/`, a role only with the roles' boundary and a user only with the users' boundary, both tagged `ManagedBy = Clutter`.** Every `aws_iam_role` a template renders needs `path = "/clutter/"`, `permissions_boundary = var.permissions_boundary_arn` and that tag, every `aws_iam_user` needs the path, `permissions_boundary = var.user_permissions_boundary_arn` and the tag, and every `aws_iam_instance_profile` needs the path, or the deploy fails with access denied. The roles' boundary (`ClutterPermissionsBoundary-<UniqueId>`) allows only what the rendered functions and instances use; the users' boundary (`ClutterUserBoundary-<UniqueId>`) allows only reads on buckets and tables named `c????????-*`, the deployment prefix B gives every name. Both are under `/clutter/` and deny all of IAM; a role or user that needs more needs it added there. A's deployer (`fargate/ecr-scripts/terraform-deployer/entrypoint.sh`) derives the roles' boundary ARN and B's AWS connector (`render.go`) derives both from the role's ARN, so the role and boundary names change only with them.
- **B's run tasks sit in their own subnets (`modules/adapter-service/network.tf`), whose network ACL refuses every private, shared and link-local address.** Never launch a run task in the public subnets B API and the load balancer use, and never give the run subnets a route or rule into the VPC: a run connects to addresses a customer chose.
- **ECR repositories are immutable, so a tag can be pushed once.** Every image (A's two runners, B's two, the website) runs under a version tag from `prod.tfvars`, and the variables refuse `latest`. A changed image needs a new tag; `deploy.sh --a-images`, `--adapter-images` and `--site-image` push with the tags the apply uses.
- **The website's image bakes in A's and B's addresses when it is built.** B's is `https://` and `site_domain`. `deploy.sh --site-image` reads A's address from the `api_invoke_url` output, so it needs a state where A's API exists (the first deploy runs without it); an apply that changes that address needs a new `site_image_tag` and another `--site-image` run, and the deploy says so.
- **One load balancer, one name, routed by path.** B's load balancer (`modules/adapter-service/alb.tf`) serves `site_domain` only: `/v1/*` and `/healthz` go to B API, everything else to the website (`modules/website`), and any other name gets a 404. A website route under `/v1` or `/healthz` would never be reached; a new B route outside `/v1/` needs the path rule widened. B's address in the website is the site's own origin. The site's origin for CORS (`local.frontend_url` in `main.tf`) is derived from `site_domain`; never add a second variable for it.
- **The website runs in its own ECS cluster, never B's.** B API's task role may stop any task in `clutter-adapter`; keeping the website out of that cluster keeps it out of that role's reach.
- **A new route's integration and CORS modules go in the `depends_on` of `aws_api_gateway_deployment.clutter-api` in `main.tf`.** The deployment fails while any method lacks its integration; `test-deploy.sh` fails until the list is complete. Its trigger hashes the files that define the API, so a route change redeploys the `prod` stage on the next apply.
- **A route change here is also a devserver change.** `go -C backend/devserver test ./...` parses `main.tf` and fails until `backend/devserver/internal/routes/routes.go` matches (paths, methods, authorizer, timeouts, environment keys).
- **The AWS provider constraint is `>= 4.0.0` with no upper bound**, and no `required_version` is set. Pin both before the next apply.

`backend/infra-state-bootstrap` bootstraps the S3 bucket and DynamoDB lock table for this folder's own state.
