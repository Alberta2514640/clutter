# Decisions

One entry per decision (an ADR, architecture decision record): the date, the status, what was decided, why, and what would change it. An entry is "proposed" until its pull request is approved by the team (and the client, for scope or hosting), then "accepted". A superseded entry stays, marked with what replaced it.

## ADR-001: Capability-based provider adapters, not a lowest common denominator (2026-10-26, proposed)

Each cloud provider declares the resource types it supports and the canvas shows only those. Why: Patrii has no serverless, API gateway or managed NoSQL table, and a common-denominator model would remove those from AWS users too. Prior art that works this way: Terraform providers, Crossplane compositions, Cluster API providers. Would change if: the client wants one abstract diagram that deploys unchanged to several clouds. Revised 2026-11-13 by ADR-014: diagrams are drawn in building blocks that several clouds share, and each connector still declares what it supports, so this stays capability-based. Revised 2026-10-30: the first cut was a `Provider` interface (`Resources`, `Validate`, `Render`, `Regions`, `Credentials`, `VerifyAccount`, `RunnerEnv`, `StateBackend`; git commit `7b49222`). It became the connector interface in `docs/architecture/system-b-adapter-layer.md`: `Resources` became `Manifest`, `Regions` moved into the manifest, and `Render`, `RunnerEnv` and `StateBackend` moved inside the shared Terraform runner.

## ADR-002: Terraform stays the engine for every provider (2026-10-26, proposed)

Adapters emit HCL for an existing Terraform provider; Clutter does not call cloud APIs to create resources itself. Why: plan, apply, state and drift handling are already solved there, and the runner and logs already speak Terraform. Would change if: a target cloud has no Terraform provider and no OpenStack-compatible API.

## ADR-003: Patrii is targeted through public OpenStack APIs first, its own provider second, and never its console's private API (2026-10-26, proposed)

Why: the standard OpenStack Terraform provider and Keystone application credentials are documented and portable to other OpenStack clouds; Patrii's own provider is not released; the console API is undocumented and changes with each build. Contested: the second research run on the same date recommends coding against the console's REST API now (Path C in `system-b-adapter-layer.md`), since it is the only surface that works today and Patrii's homepage never names OpenStack services. Would change if: Patrii states it will not expose OpenStack endpoints and no provider is planned, or publishes an OpenAPI file and calls its REST API the supported surface.

## ADR-004: A stays SaaS on AWS; B is one container that we host or others self-host (2026-10-26, revised 2026-10-30, proposed)

Why: moving A off Lambda and API Gateway is a separate project, and nothing about Patrii requires it before a Patrii connector works. B1 is by definition a service other people can run, which they cannot do with Clutter's API Gateway and Lambdas, so B is one Go service in a container plus a Terraform runner, hosted by us beside A or self-hosted. Keeping connection credentials and state behind the connector interface leaves room to run the runner inside a customer's cloud. The 2026-10-26 version kept the deployer BYOC-ready through `RunnerEnv` and `StateBackend` on a provider interface; those are now the connection credentials and the runner's state backend. Would change if: the client needs Canadian-only hosting of Clutter itself (data residency, CLOUD Act exposure), in which case hosting on Patrii or BYOC moves before stage 7.

## ADR-005: The central standard is a versioned inbound API over Clutter's own model (2026-10-26, proposed)

Other products, and people, call one `/v1` API. It is B API (ADR-006): it sits beside A's handlers, reuses A's sign-in and organization model, and puts connectors behind it. Its objects, revised 2026-10-30 to follow the team's plan: organization, project, desired state, target, instance, workspace, run, catalog (`docs/architecture/system-b-adapter-layer.md`); revised 2026-11-13 by ADR-014: connection replaces instance in the UI, deployment is added, and workspace is dropped. The 2026-10-26 draft renamed project to workspace; that rename is dropped, because the plan uses workspace for an environment inside an instance. Why: the existing org, project and diagram path with its membership check is sound enough to wrap, while the internal routes are inconsistent (ids in paths and queries, mixed names, no error envelope, no idempotency). Freezing them as the public contract would freeze those gaps. Would change if: the only consumers are Clutter's own frontend, in which case the outbound adapters alone are enough.

## ADR-006: Build B next to A (Option 1), reuse A only at named seams (2026-10-30, proposed)

The adapter layer (B) is new code with its own tests, beside today's AWS system (A), not a rewrite of A. B touches A at four named seams only: the UI target choice, shared sign-in and the JWT authorizer, the shared database (a target field on projects, new target, instance and credential tables), and the security fixes on paths B shares with A. Reusing other A code (Option 2) is the fallback and is decided case by case. Turning A into the adapter (Option 3) is a later destination reached piece by piece, never the first move. Why: A is a complete, tested application, and every change to it means retesting every AWS path. Source: the team's plan in `docs/architecture/system-b-team-plan/`. Trade-off: B duplicates some of A (job tracking, logs) until AWS moves into B. Would change if: B needs so much of A that the duplicated code costs more than A's retest would. Revised 2026-11-13 by ADR-014: B adds deployments instead of a target field on projects, reads A's linked AWS roles, and reuses A's templates for its AWS connector; A's own code changes only where stage 1 makes it shareable: its template loader and JWT check move into `generic`, and the generator reads the environment's region (`docs/architecture/implementation-plan.md`). The UI seam is now B's own editor and Connections page, chosen per diagram, not a target choice on A's screens.

## ADR-007: B0 (SaaS) first, then B1 (self-hosted), then B2 (internal) (2026-10-30, revised 2026-11-08, proposed)

Revised 2026-11-08: B0, B run by us as a hosted service, comes first, because it proves B with the least setup and support work; B1 follows when a customer asks to run Clutter on their own servers. B stays portable (any Postgres, any S3-compatible store) so B1 remains possible. B1 needs nothing we do not have. B2 needs to know how targets such as TierHive and PatriCloud run inside the companies that use them. Build order: connector interface, the B skeleton run as B0, and General; then PatriCloud and TierHive; then B2. Would change if: a partner hands over the details B2 needs, or the client wants B2 first. Revised 2026-11-13: the full order, General's OpenStack connector, then B's AWS connector, then the rest, is the stages in `docs/architecture/implementation-plan.md`. B1 is later; B2 is later still, and whether to do it at all is a separate decision.

## ADR-008: General comes first, and covers targets without an API (2026-10-30, proposed)

General has two modes: Terraform with a provider the connection names, and existing hosts over SSH with Ansible. Revised 2026-11-13: the provider comes from an allow-list Clutter maintains, OpenStack first (ADR-014, ADR-017). General is a family: one connector per approved provider (`general-openstack`, later `general-digitalocean`) plus one for existing servers (`general-ssh`), sharing one kit, and users pick a cloud by name. A new cloud reachable through an approved Terraform provider is a new General connector, so Patrii's OpenStack endpoints or its own provider, and a future TierHive provider, arrive through General; a cloud gets a named connector of its own only when no approved provider reaches it or Clutter must drive its own sign-in flow (AWS, Patrii's console API). Why: it needs no partner, and it is the only way to reach TierHive and Patrii today, since neither has a public API (`docs/research/tierhive/2026-10-30-tierhive-research.md`, `docs/research/patricloud/2026-10-26-patricloud-research.md`). Would change if: the client defines General differently.

## ADR-009: A local dev gateway runs System A without AWS (2026-10-30, proposed)

`backend/devserver` runs A's real, unchanged Lambdas on one machine: a gateway on loopback that stands in for API Gateway and the authorizer, Postgres in Docker, and a dev-only sign-in. It never ships and never deploys. It refuses to start with a secret it did not generate, a non-loopback address or a non-loopback database, and every AWS call is refused locally. It has its own Go module, so A's `go.mod` is untouched, and a test fails if its route table drifts from `backend/infra/main.tf`. B's local development reuses it rather than adding a second launcher. Why: A was built to run only in AWS, the capstone account is gone, and deploying A as it is would expose the open security defects; this is the only way to check A, and the seams B touches, without an account or cost. Trade-off: about 2,900 lines of tooling to maintain, and it can differ from real API Gateway (request-model validation is not applied). Would change if: we get a dev AWS account and a deploy pipeline that make a local run unnecessary, or the gateway's behaviour drifts from API Gateway in a way that misleads.

## ADR-010: Three environments: local, dev and prod, sharing nothing (2026-11-04, superseded by ADR-015)

Clutter runs in three places with one job each: local (each developer, no accounts), dev (the team's real-cloud proof) and prod (customers). The same code runs in all three and only configuration differs. They share no AWS account, database, Google client, secret or state bucket, and change moves one way, from local through `main` and dev to prod. `docs/architecture/environments.md` holds the table. Why: a mistake in dev must be unable to touch prod, and the team needs one clear answer to "what is different where". Trade-off: two sets of accounts to look after. Would change if: the client wants one AWS account with separate stacks to save cost, which is weaker isolation.

## ADR-011: C is A + A2 + B; A2 extends A without changing it (2026-11-04, proposed)

The whole app, C, has three parts. A is Clutter as built. A2 is the extension that makes A run and test without AWS (`backend/devserver`), by answering the outside calls A makes rather than editing A. B is the adapter layer. New local and test abilities go in A2. A itself changes only for security and bug fixes and for small named seams (ADR-006). Why: A stays exactly as delivered and every change stays easy to see, and it replaces a proposal to rework all 33 handlers, which would have changed all of A at once. Trade-off: A2 depends on A's internals, such as which AWS calls it makes, so a change in A can break it. One exception, chosen by the person: the **Link fake account** button sits in A's frontend, shown only in a development build with a loopback API, because it is the one way to unlock the canvas for a Google sign-in locally. Would change if: A2 keeps breaking when A changes, or customers need to run A2 themselves, which would make it a shipped product. Note 2026-11-14: ADR-024 narrows "A changes only for security and bug fixes" to A's backend and A's editor; the website's shared screens (sign-in, onboarding, organizations, projects, connections, the landing page) are reworked as one product. Note 2026-11-14: the local-only Link fake account button also sits in the AWS link flow on the Connections page, as one shared component; it never renders in a production build. Note 2026-11-14: one bug fix in a template A and B share. The API Gateway template no longer renders a request validator, because no method ever used it; A's golden files lose those seven lines each and nothing else in A's output changes. B's other fixes from the review of its rendered Terraform sit in B's own files and B's network template.

## ADR-012: Reading generated Terraform is a product feature of A (2026-11-04, accepted)

Every user with a linked account, in every environment, can read and download the Terraform for a saved diagram, in the editor. One new authenticated route reads what A's real generator wrote, and the generator records a status beside the files, so the editor can warn when the files are from an older save. It is an agreed exception to ADR-006: a new feature in A, plus a small change to the generator. The editor panel comes from a teammate's `feat/local-terraform-preview` branch; that branch's separate disk generator is not used, so what users see is always what A produces. Why: a user should see the code that will run in their account, and A offered no way to do that. Trade-off: it depends on generation working, so in cloud it needs the Supabase webhook and phase 0 item 1. Would change if: users need a preview before saving, which needs generation on demand. Note 2026-11-14: ADR-018 retires the Supabase webhook; generation is now a signed-in call the editor makes after each save, so the preview no longer depends on a webhook.

## ADR-013: Clutter is one hosted product where users bring their own cloud accounts (B0 + 2.1) (2026-11-13, proposed)

Clutter is run by us as SaaS (B0), and diagrams build in the user's own cloud accounts, which they link on a Connections page (world 2.1), in the way Brainboard works. Clutter-managed accounts, where Clutter owns the clouds users build in and bills them (2.2), are not in scope. Live multi-user collaboration is built by another team on top of this work; we keep the diagram document stable for them. Why: 2.1 is what A already does for AWS, and 2.2 is a different business (we would pay every user's cloud bill and need billing, abuse limits and liability cover) that adds nothing to the adapter layer. Would change if: the client wants to resell cloud capacity. Revised 2026-11-13: a narrow form of 2.2 may come later as an optional "use Clutter's sandbox" connection, into a separate Clutter-owned account (never the account Clutter runs in), with a per-user spending cap and automatic clean-up; connections are designed so it is one more connection type.

## ADR-014: One diagram, many deployments, and AWS as a B connector too (2026-11-13, proposed)

A diagram is drawn once in building blocks (VM, network, firewall, volume, bucket, function, table, HTTP API) and can be deployed to several linked clouds. Each deployment is the diagram bound to one connection, with its own settings, state and runs; the capability check shows per deployment what that cloud cannot build. AWS joins B as a connector that reuses A's customer templates and role link, so a new diagram can deploy to AWS beside other clouds; A stays unchanged and keeps serving existing AWS diagrams until B's AWS connector covers it. General's first connector is OpenStack (`general-openstack`), tested on DevStack, which is also Patrii's Path A. Why: choosing one cloud per diagram is poor for users, and per-target diagrams would need to be redrawn for every cloud; reusing A's templates keeps the AWS Terraform in one place. Trade-off: AWS is reachable through two paths until A's flow retires, and building blocks need a mapping per connector. Not in the first build: one diagram spread across several clouds, because edges across clouds cannot carry permissions. Replaces "target-native nodes first" in ADR-001's design and the project target field in ADR-006. Would change if: the client wants each diagram tied to one cloud, or the block mappings prove too lossy for real diagrams. Revised 2026-11-13 after an independent review and a code check: A's template-loading code moves out of its `internal` package into `generic` so B can import it, guarded by a golden test that keeps A's output byte-identical; B has its own edge-to-IAM step; the AWS role template trusts both A's and B's runner roles, and each connection records its role-template version; a building-block diagram carries `engine: "blocks"` and A's generation skips it; a deployment can leave out a block its cloud cannot build; blocks are addressed by node id and cloud names carry a deployment prefix; a connection, diagram, project or organization with live deployments cannot be deleted until they are destroyed. Note 2026-11-14: ADR-020 reverses "Not in the first build: one diagram spread across several clouds". One deployment can now place blocks on several clouds, and permission edges across clouds get scoped keys.

## ADR-015: Two environments: local and one cloud, run with prod rules, in ca-central-1 (2026-11-13, proposed; supersedes ADR-010)

Clutter runs locally (each developer, no accounts) and in one cloud environment in the client's AWS account in `ca-central-1`, deployed with `npm run deploy -- prod`: only from a clean `main`, with a typed confirmation and no tear-down command. Diagrams in the cloud deploy into our own test accounts: a second AWS account acting as a user, and an OpenStack (DevStack on a virtual machine, switched on for demos) until Patrii opens. Why: there are no outside users yet, all testing happens locally and in CI, and one set of accounts is simpler for the client and the team; a Canadian region suits a Canadian product. Trade-off: a risky change has nowhere to be tried in a real cloud before it is live. Would change if: real outside users arrive, which adds a separate test environment (the deploy command already takes the environment as a parameter).

## ADR-016: User cloud credentials: borrowed where possible, otherwise an encrypted secret, never a password (2026-11-13, proposed)

AWS keeps A's model: a role the user creates, short-lived keys at each run, nothing permanent stored. Other clouds use the most limited credential they offer (an OpenStack application credential, an API token, an SSH key), stored in AWS Secrets Manager in B0, one secret per connection, with only its reference in Postgres; locally A2 encrypts it with a key from its own config. The runner reads it for one run and never logs it. Deleting a connection deletes its secret. Why: Clutter holds access to other people's clouds, so a leak must expose as little and as briefly as possible. Would change if: B1 is built, where the customer's own secret store takes this place.

## ADR-017: Each run is isolated; only Clutter writes the Terraform it runs (2026-11-13, proposed)

B starts one short-lived task per run, with no database or secret-store access; a broker in B's API hands it only that run's credentials (short-lived session keys for AWS, the one connection's token otherwise). B renders all Terraform from building blocks with its own templates; General supports only providers on an allow-list Clutter maintains, not any provider a user names; rendered Terraform with provisioners or the `external` or `http` data sources is refused before `plan`; `TF_LOG` is never set; B's run tasks use their own cluster. Why: a runner holds the keys to a user's cloud. A's runner today can assume every customer's role and is handed the database string that holds every external id, so a single injected command reaches every tenant (found by the 2026-11-13 review; added to phase 0). Trade-off: General is narrower than "any Terraform provider", and each run pays a container start. Would change if: a provider is needed that cannot be allow-listed, in which case it runs in its own isolated runner.

## ADR-018: Generation is a signed-in call made after save; the Supabase webhook is retired (2026-11-13, proposed)

`POST /terraform-engine` gets the JWT authorizer like every other route. After a save succeeds, the frontend calls it with the user's token and only `projectId` and `diagramId`. The handler checks that the caller is a member of the project's organization and that the diagram belongs to that project (the shared ownership helper, phase 0 item 5), then loads the diagram from the database; it never trusts diagram data in the request body. Error bodies are generic. The Supabase database webhook, and A2's stand-in for it, are removed. `GET /resources` stays public, because it serves only the static resource catalog, and its Terraform says so. Why: the route was public and trusted `project_id` from the body, so anyone with a project id could overwrite another tenant's generated code (phase 0 item 1), and the webhook was configured outside the repo, so nothing in the repo triggered generation. Trade-off: generation now runs only when a client asks for it; a diagram changed by another path is not regenerated until the next save. Would change if: B's save path needs generation for building-block diagrams, which B does in its own API.

## ADR-019: A role ARN is checked by B when it becomes a connection, not by A's account link (2026-11-13, proposed)

Phase 0 item 8 asked A's `submit-role-arn` to prove a role with STS before storing it. Doing that means trusting a third Clutter principal (the submit Lambda's role) in every customer's role, next to A's runner and B's runner. Instead, A keeps its format checks, and B proves the role with STS (`VerifyConnection`) when a user turns a linked role into a connection, and again before each run. Why: the external id is unique per organization and bound to it (A assumes a role only with the external id it issued to the caller's organization, and B makes an AWS connection only from a linked role of the caller's organization, never from a pasted external id, since the id appears in the stack link the organization's members see), so the STS check at link time only catches a mistyped ARN sooner; one fewer trusted principal in the customer's account is worth more than that. Trade-off: on A's own deploy path (until it retires), a wrong ARN shows up at the first deploy instead of at the link. Would change if: A's AWS flow stays long enough that the late error costs users real time.

## ADR-020: A diagram can be split across clouds in one deployment, with scoped keys created automatically (2026-11-13, proposed)

One deployment can place each block on a different linked cloud of the same organization. Clutter applies the clouds in dependency order, passes outputs across (addresses, endpoints, bucket names) and opens only the firewall rules the diagram's edges need. When an edge needs permission in another cloud (a VM on OpenStack reads an S3 bucket), Clutter creates a key in that cloud that can do only what the edge allows (read that bucket), hands it to the block at first boot (cloud-init), never shows it to anyone, and deletes it when the deployment is destroyed. If one cloud's apply fails, Clutter destroys what the others built in that run, so nothing is left half built. Why: the point of the adapter layer is that a user can build a system across clouds without manual steps; refusing permission edges would leave the user to wire keys by hand. Trade-off: a long-lived, narrowly scoped key lives inside the user's VM for the deployment's life; a stolen key reaches only what the edge allowed. Would change if: a cloud offers workload identity across clouds (for example AWS IAM Roles Anywhere with a certificate Clutter issues), which would replace the stored key with short-lived credentials. Revised 2026-11-13 as built: a cross-cloud edge opens no firewall rule, because outbound traffic is already open on both clouds and an inbound rule would need the source's address before the source exists; an address edge (VM to VM) therefore requires the target to be public. A failed apply is rolled back only when the deployment held nothing before the run; a live deployment is never torn down by a failed change, and its failure says so. Edges that can cross clouds are VM to VM (address) and VM to bucket or table (permission); any other cross-cloud edge is refused before anything runs.

## ADR-021: Clutter becomes one system (C) after B passes on real AWS (2026-11-13, proposed)

The end state is one system: B's service plus A's core (sign-in, users, organizations, projects, diagrams, the AWS account link) under one `/v1` API, one website on `/v1` only, and one deploy path; A's Lambdas, API Gateway, A's diagram editor, A's runners and queue, and A2's Lambda emulation are deleted. It is built only after B's AWS path passes the stage 7 tests on real AWS, so A's AWS path stays as the fallback until then. Why: the person chose to prove B on real AWS before removing anything that works. Trade-off: credentials day sets up A's Lambdas and runners as well, which are removed afterwards. Would change if: real AWS cannot be had for long, in which case LocalStack plus the local tests are the bar instead.

## ADR-022: Cloud logos are neutral tiles; service icons only where their owner allows diagram use (2026-11-13, proposed)

Clutter shows a neutral tile with the cloud's short name ("AWS", "OS") wherever a cloud is named, and shows a service's own icon only where its owner licenses that use: AWS's Architecture Icons, which AWS allows customers and partners to use in architecture diagrams, appear in the editor's AWS view (EC2, VPC, EBS, S3, Lambda, DynamoDB, API Gateway); OpenStack's services keep neutral icons with their names (Nova, Neutron, Cinder). Why: AWS's trademark guidelines (updated 2026-11-05) allow fair use of its name as plain text only, not its logo, and the OpenInfra Foundation does not allow the OpenStack logo in a commercial product without a signed licence; its project mascots are licensed CC BY-ND but may not brand a product. Sources and dates are in `frontend/clutter/public/clouds/README.md`. Trade-off: the connection cards and deploy rows are less recognisable than with real logos. Would change if: AWS gives written permission, or Clutter earns an "OpenStack Compatible" licence; swapping a logo in is then one file and one manifest key.

## ADR-023: One public name; the website runs on Fargate behind B's load balancer (2026-11-13, proposed)

Clutter answers on one name (`site_domain`, for example `app.example.com`): B's load balancer sends `/v1/*` and `/healthz` to B's API and everything else to the website, which runs as its own small Fargate service in its own cluster, with its image in Clutter's ECR; one ACM certificate and one DNS record cover it, and `npm run deploy -- prod --site-image` builds the image with A's API address, the site's origin and the Google client id taken from Terraform. A's API keeps its API Gateway address until C (ADR-021). Why: users see one address, credentials day needs one DNS record and one certificate, the website and B's API share an origin (no cross-site setup), and nothing is hosted outside the client's AWS account in Canada. Trade-off: an always-on container costs a little more than static hosting, which a Next.js server cannot use. Would change if: the client prefers a managed host such as AWS Amplify, or a marketing site on the bare domain (one more name on the certificate).

## ADR-024: The website is one app for A and B, and its screens are reworked as one product (2026-11-14, proposed)

The website (`frontend/clutter`) is the one front door for A and B: sign-in, onboarding, organizations, projects, connections, the landing page and the public pages are shared, and only the diagram editor differs (A's for older AWS diagrams, B's for building-block diagrams, chosen per diagram). Those shared screens were reworked in one pass for a clear first-run flow, phone layouts, one visual style and plain wording, which goes beyond ADR-011's "A changes only for security and bug fixes": ADR-011 still holds for A's backend and A's editor, not for the shared screens. Why: users see one product, so its screens cannot follow two rules, and the old screens had mock data (members, workspaces), dead links and no phone layout. Trade-off: more of `frontend/clutter` differs from the client's `main`, and the reworked screens are covered by type checks, unit tests on their logic, the smoke test and a browser walk-through, not by end-to-end tests. Would change if: the client wants A's original screens kept as they were.

## ADR-025: In B's editor, networks are boxes and every other link is a line (2026-11-14, proposed)

B's building-block editor draws a network as a resizable dashed box labelled with its name and address range, and a VM inside a box runs in that network. Containment means exactly the diagram's VM-to-Network edge: the saved document keeps that edge, so B's API, the connectors and their manifests are unchanged, and an older diagram opens with each VM in the box of its first network edge (a second network edge stays a line, so nothing saved is lost). A VM sits in one box at a time; every other block stays free on the canvas, and every other link is a line. While a line is drawn, only the blocks the clouds in play can link to light up, and a refused line says why in one short line from the manifests (each edge's `why` and, where a source links to one target only, its `rule`). Each block kind has a one-line `summary` in the manifest. A's older editor is unchanged. Why: a person with no cloud background reads "this server is in this network" from a box at a glance, while a line to a network reads like any other link and hides that a VM runs in one network on AWS. Trade-off: the canvas holds the network edge as containment, so the editor converts on load and on save, and OpenStack's VM on two networks shows one as a box and the other as a line. Would change if: a block other than a VM needs to sit inside a network (a load balancer or a database service), or a cloud nests networks.
